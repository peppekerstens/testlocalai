## Findings

**Note on the "Comparison vs previous report" table above**: the
"regressed" verdicts on `reason-config-validity`/`reason-trace`/
`reason-coverage` are an artifact, not a real per-draw change. The
"previous" report (`report-reason-20260804-150043.md`) was measured
against 7 of 9 `reason-*` SPEC.md files that still had
`lfm2.5-1.2b-thinking`'s "OUTPUT DISCIPLINE" block baked into the
shared file (found and fixed same-day, commit `cd77859`) — marked
INVALID in that report. This report is the actual, first, genuinely
bare Phase 1 baseline for this model+role; there is no valid prior
report to diff against. All 9 `finish_reason=stop`, zero truncation.
Single draw — every verdict below is n=1, not a reliability sample
(sample-size caveat, per AGENTS.md).

- **`reason-config-validity` (FAIL).** `verify.sh`: `unrelated token
  present: 'idField'` and `unrelated token present: 'tokenTemplate'`.
  The model reasons to the correct conclusion (the `owner` value under
  `defaultContact` doesn't exist as an `entities` key) but pads its
  step-by-step trace with field names copied verbatim from the input
  config's `EntityRule` schema (`idField`, `tokenTemplate`) that
  `verify.sh` explicitly forbids as noise. New idiom, not previously
  documented for this model (only tested on the docs role before).

- **`reason-diagnose` (FAIL).** `verify.sh`: `missing required token:
  'requireEnv'`. The model correctly identifies the root cause
  (`CW_PRIVATE_KEY` unset causes startup abort) and quotes the exact
  log message, but never names the specific validation function
  (`requireEnv`) the task expects cited. New idiom for this model:
  correct diagnosis, but the answer stays at the symptom/env-var level
  instead of citing the specific code-level mechanism enforcing it.

- **`reason-trace` (FAIL).** `verify.sh`: `missing required token:
  're-initialize'`. The model traces the restart → Map-wipe →
  session-random token regeneration → 400 chain correctly and in the
  right causal order, but never uses the specific word "re-initialize"
  the task requires. Same shape as `reason-diagnose`: reasoning is
  substantively correct, but a single required exact phrase is absent.

- **`reason-compare` (FAIL).** `verify.sh`: `missing required token:
  'config was valid'`. The model picks the correct candidate (A) with
  a coherent justification covering both required parts of the fix,
  but never states the exact phrase "config was valid" the task
  requires as evidence it understood the boot-time invariant being
  restored. Same idiom as the two above.

- **`reason-multihop` (FAIL).** `verify.sh`: `hop 1 ... PASS`, `hop 2
  (names addressLine2 specifically) ... PASS`, but `missing hop 2
  detail: doesn't name entities.company specifically`. Closest to
  passing of the 6 failures — both reasoning hops are substantively
  present, but the second hop's answer doesn't cite the specific YAML
  path (`entities.company`), staying one level more generic
  (`entities.<EntityName>.fields`) than required. Same underlying
  idiom (correct reasoning, imprecise exact-identifier citation), one
  specific dropped requirement rather than a whole missing token.

- **`reason-coverage` (FAIL).** `verify.sh`: categories 1, 2, 4, 5
  present, but `missing category 3: no excluded field
  (dateResolved/severity/slaStatus/...) named` — the model's 5-item
  checklist covers the obfuscation, lookup-resolution, empty-result,
  and missing-optional-object cases well, but never covers the
  excluded-field-omission case at all (not even with a wrong specific
  field name — the whole category is missing from the list).
  Different idiom from the other 5: this is a missing required
  *element*, not an imprecise/paraphrased required *token*.

**Idiom summary**: 4 of 6 failures (`config-validity`, `diagnose`,
`trace`, `compare`) plus part of a 5th (`multihop`'s hop 2) share one
idiom — **substantively correct reasoning that lands on the right
conclusion but doesn't reproduce the exact required vocabulary/phrase
`verify.sh` checks for verbatim.** This is a new idiom for
`qwen3.5:9b`, not seen in its docs-role work (closest analog there was
`doc-verbatim`/`doc-surgical`'s exact-text-fidelity gap, but those were
about reproducing *given* source text, not about spontaneously using a
specific required word/phrase while reasoning in its own words) — worth
checking against other models' reasoner idioms in the Research phase
next. `reason-coverage` is a distinct idiom (a whole missing checklist
item, not an imprecise one). `reason-config-validity` is also distinct
(extraneous copied-in noise, not a missing element).

## Suggested next steps

- **`reason-diagnose`/`reason-trace`/`reason-compare` (shared idiom,
  batch-testable as one lever first per AGENTS.md's Steering-phase
  guidance)**: try a reminder that the answer must include the task's
  own named terms/phrases verbatim, not a paraphrase of them — the
  reasoning is already correct, this is a precision-of-output-vocabulary
  problem, not a comprehension problem. Single draw so far; this is
  Tier 1's first genuine attempt for these 3 tasks, not yet gated.
- **`reason-multihop`**: same lever as above is plausible (it's the
  same idiom, just one dropped detail rather than a whole token) —
  worth including in the same first batched probe rather than treating
  as fully separate, per AGENTS.md's "shared candidate as first probe"
  guidance. Re-split into its own branch immediately if the batched
  result is mixed.
- **`reason-config-validity`**: needs its own, different lever (the
  problem is opposite — too much copied-in noise, not too little
  precision) — an explicit "don't restate the input schema's other
  field names in your reasoning" instruction. Do not batch with the
  3-4 tasks above; the fix shape is different (suppress copying vs.
  demand exact phrasing).
- **`reason-coverage`**: needs its own lever — the model needs to be
  prompted to explicitly enumerate *all* the listed requirement
  categories (obfuscation, lookup-resolution, exclusion, empty-result,
  missing-optional-object) before writing, not just the ones that come
  to mind first. A checklist-completeness reminder, not an exactness
  reminder.

  Research phase (cross-model idiom check + external research) runs
