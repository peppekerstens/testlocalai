Step (1): A restart drops every active MCP session because session state is only an in-memory `Map` in `src/http/app.ts` named `transports`, keyed by `mcp-session-id`, with no persistence layer. Step (2): In `session-random` token mode, every restart changes every token, so a consumer that persisted a token expecting it to remain meaningful loses that ability at the next restart. Step (3): On the client’s next non-initialize request after the restart, the old `mcp-session-id` is no longer present in `transports`, so the request has no valid session ID and the client must re-initialize; the document’s analogous missing-session failure is a `400 No valid session ID provided`. Step (4): The exact mechanism is the in-memory `transports` `Map` in `src/http/app.ts`, keyed by `mcp-session-id`. Final answer: the established session is destroyed and its `session-random` token is invalidated, so the client cannot resume and must re-initialize.
